# Database Design

## Purpose

PostgreSQL is ForgeQueue's durable source of truth. Job metadata survives API
and worker restarts, while image bytes remain in the shared local media volume.
The database stores file locations rather than binary image data.

## Jobs table

The `jobs` table contains one row for each image-processing job.

| Column | PostgreSQL type | Nullable | Purpose |
| --- | --- | --- | --- |
| `id` | `UUID` | No | Primary key generated by the application |
| `status` | `VARCHAR(20)` | No | Current lifecycle state |
| `input_path` | `TEXT` | No | Location of the validated input image |
| `output_path` | `TEXT` | Yes | Result location after successful processing |
| `error` | `TEXT` | Yes | Processing or queue-publication error |
| `created_at` | `TIMESTAMPTZ` | No | UTC job creation time |
| `updated_at` | `TIMESTAMPTZ` | No | UTC time of the latest state change |

The schema is managed by Alembic. Its status check constraint currently permits
`PENDING`, `QUEUED`, `PROCESSING`, `COMPLETED`, `FAILED`, and `RETRYING`.

## Design decisions

### PostgreSQL owns state

Redis transports small messages containing a job UUID and attempt number. A
worker loads the authoritative job from PostgreSQL before processing it. This
keeps queue delivery separate from durable business state and makes duplicate
deliveries safe to detect.

### Required input and optional output

Every valid job has an input location at creation. An output does not exist
until processing succeeds, so `output_path` is nullable.

### Timezone-aware timestamps

`TIMESTAMPTZ` records an absolute moment. ForgeQueue stores UTC values so API
processes, workers, PostgreSQL, and future cloud services share one timeline.
Timezone conversion belongs in the presentation layer.

### UUID identifiers

UUIDs can be generated independently without coordinating a database sequence,
which suits multiple API processes. They also avoid exposing an easily
enumerable sequence. A UUID is only an identifier—not an authorization check.

### Domain mapping

The repository layer converts SQLAlchemy rows into typed `Job` objects,
including strings to `JobStatus` values and path strings to `pathlib.Path`.
Routes and services therefore do not depend on raw database rows.

## Cross-system consistency

PostgreSQL, Redis, and the filesystem do not participate in one atomic
transaction. The current implementation reduces common inconsistencies:

1. The API validates and writes the input image.
2. It creates the database row.
3. It moves the job to `QUEUED` and publishes its UUID to Redis.
4. If database creation fails, it removes the input file.
5. If publication fails, it marks the job `FAILED` and removes the input file.

A process crash between the database commit and queue publication can still
leave an unpublished job. A production system should use a transactional
outbox and a publisher that reliably transfers committed outbox records to
Redis.

## Indexes and future queries

The primary key indexes lookup by job ID, which is the current API query. A
multi-user job listing would add an owner identifier and a composite index such
as `(owner_id, created_at DESC)`. Indexes should follow real access patterns
rather than being added speculatively.
