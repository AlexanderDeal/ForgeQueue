# Database Design

## Purpose

ForgeQueue currently stores jobs in an in-memory dictionary. That is useful for
Phase 1, but all job metadata disappears when the API process restarts. In Phase
2, PostgreSQL will become the durable source of truth for job metadata.

Uploaded and processed image files will remain on the local filesystem during
this phase. PostgreSQL will store their locations, not the image bytes.

## Jobs Table

The `jobs` table will contain one row for each media-processing job.

| Column | PostgreSQL type | Nullable | Purpose |
| --- | --- | --- | --- |
| `id` | `UUID` | No | Primary key generated by the Python application. |
| `status` | `VARCHAR(20)` | No | Current state in the job lifecycle. |
| `input_path` | `TEXT` | No | Location of the uploaded input file. |
| `output_path` | `TEXT` | Yes | Location of the processed result after successful processing. |
| `error` | `TEXT` | Yes | Error information when processing fails. |
| `created_at` | `TIMESTAMPTZ` | No | Absolute time at which the job was created. |
| `updated_at` | `TIMESTAMPTZ` | No | Absolute time of the latest lifecycle change. |

## Job Statuses

Phase 2 supports these statuses:

- `PENDING`
- `PROCESSING`
- `COMPLETED`
- `FAILED`

The status column will use text with a database check constraint. Later phases
can extend the lifecycle with statuses such as `QUEUED` and `RETRYING`.

## Design Decisions

### Required input and optional output

Every valid job needs an input location when it is created. An output location
does not exist until processing succeeds, so `output_path` must be nullable.

### Timezone-aware timestamps

`TIMESTAMPTZ` represents an absolute moment in time. ForgeQueue will store
timestamps in UTC so API processes, workers, PostgreSQL, and future AWS services
share one consistent timeline. Timezone conversion should happen only when a
timestamp is displayed to a user.

### UUID identifiers

UUIDs can be generated independently by the application without requesting the
next database sequence value. Their collision probability is extremely low,
and they do not expose an easily enumerable sequence in public job URLs. A UUID
is still only an identifier and must not be treated as authorization.

### Mapping database rows to Python objects

The database store or repository layer will convert database values into domain
types. For example, it will convert the string `"PENDING"` into
`JobStatus.PENDING` and an input-path string into a `pathlib.Path`.

FastAPI routes and `JobService` should continue to use typed `Job` objects rather
than raw database rows or strings.

## File and Transaction Failure Scenario

A PostgreSQL transaction cannot roll back a filesystem write. If the API saves
an uploaded file and the following database transaction fails, the database row
is rolled back but the file remains as an orphan.

The application should attempt a compensating cleanup:

1. Save the uploaded file.
2. Attempt to create the job in a database transaction.
3. If the transaction fails, delete the uploaded file and re-raise the error.

Cleanup can also fail, so a production system may need periodic orphan-file
cleanup in addition to immediate compensation.

## Initial Query and Index Requirements

The primary key automatically provides an index for job lookup by ID. ForgeQueue
does not yet list or filter jobs by status, so it does not need a status index in
the initial schema. Indexes should be added in response to actual query patterns
rather than speculatively.
